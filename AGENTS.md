# Правила проекта печатной платы

## 0. Как работать с владельцем проекта

- Владелец проекта не программист: объясняй простым языком, что делаем, зачем и какие есть риски.
- Перед крупным шагом дай короткий план. После шага дай резюме и способ проверки.
- Между быстрым хрупким и надёжным решением выбирай надёжное.
- Если запрос противоречит этим правилам или электрической безопасности, сначала предупреди.

## 1. Источник истины

- Исходник проекта находится в `src/` и документации `.md`.
- Каталог `build/` генерируется автоматически и вручную не редактируется.
- Ручное изменение в KiCad нужно перенести обратно в TSX-код, иначе оно будет потеряно.
- Не читать целиком большие сгенерированные файлы без необходимости: сначала использовать отчёты ERC/DRC, Circuit JSON и рендеры.

## 2. Стек и команды

- Node.js 24+, npm, TypeScript в строгом режиме.
- tscircuit описывает схему, размещение и соединения.
- `circuit-json-to-kicad` создаёт файлы KiCad.
- KiCad 10 CLI выполняет ERC, DRC и 3D-рендер.

Основные команды:

- `npm run dev` — интерактивный просмотр tscircuit.
- `npm run generate` — генерация Circuit JSON и файлов KiCad.
- `npm run lint` — TypeScript, ESLint и форматирование.
- `npm test` — автоматические тесты схемы.
- `npm run erc` — проверка схемы KiCad.
- `npm run drc` — проверка платы KiCad.
- `npm run render` — 3D-рендер платы.
- `npm run verify` — полный локальный контроль.

## 3. Работа по шагам

- Следовать `ROADMAP.md`; один большой этап делить на небольшие проверяемые шаги.
- Перед проектированием заполнить `HARDWARE.md`.
- После изменения структуры обновить `PROJECT_MAP.md`.
- Шаг не завершён, пока его проверки не прошли или исключение явно не описано.

## 4. Правила схемотехники

- Распиновки, предельные параметры и типовые включения брать только из официальных даташитов.
- Не придумывать отсутствующие параметры. Неясность фиксировать как открытый вопрос.
- Для каждого компонента указывать точный MPN, корпус и проверенный footprint до подготовки производства.
- Документировать напряжения, токи, мощность, нагрев и допустимые отклонения.
- Проверять развязку питания, защиту от переполюсовки/КЗ, ESD и безопасное состояние при запуске.
- Сетевое напряжение, аккумуляторы высокой мощности и RF требуют отдельного инженерного ревью.

## 5. Правила платы

- Зазоры, ширины дорожек, отверстия и stackup брать из требований выбранного производителя.
- Критичные цепи питания, тактирования, высоких токов и дифференциальные пары проверять отдельно.
- Авторазводка не считается доказательством качества.
- Зелёные ERC/DRC не доказывают, что устройство электрически правильно.
- Перед заказом обязательны визуальный просмотр схемы, слоёв, 3D и производственных файлов человеком.

## 6. Тестирование и Git

- Для генераторов и повторяющихся каналов писать тесты.
- Перед коммитом запускать `npm run verify`.
- Коммиты короткие: `feat:`, `fix:`, `test:`, `docs:`.
- Не пушить и не заказывать плату без явного запроса владельца.
- Секреты хранить только в `.env`; `.env` не коммитить.

## 7. Документация

- `README.md` — запуск и общий процесс.
- `ROADMAP.md` — текущий этап и следующие шаги.
- `PROJECT_MAP.md` — краткая карта файлов.
- `HARDWARE.md` — требования, компоненты, питание и производство.
- Подробности выносить в `docs/`, не раздувать этот файл.

## 8. Завершение шага

- Код и документация обновлены.
- Нужные тесты, ERC и DRC выполнены.
- Результат визуально проверен, если менялась плата.
- В `ROADMAP.md` отмечено, что сделано и что осталось.
- Дано короткое резюме для следующего шага.
